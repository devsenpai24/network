## Audit Entry 1: Bitwise Subnet Boundary Overflow in Pure-Bitwise Allocator

### 1. Context & AI Suggestion
* **Module Affected:** `netarchitect/vlsm.py` (Dynamic VLSM Allocator)
* **User Prompt:** "Implement a pure bitwise integer allocator that aligns subnets dynamically to power-of-2 boundaries without using the `ipaddress` module."
* **Buggy AI Code Snippet:**
```python
# AI's suggested block boundary alignment
def align_block(current_ip_int, block_size):
    # AI attempted bitwise alignment:
    return (current_ip_int + (block_size - 1)) & (-block_size)
```

### 2. Failure Diagnosis & Technical Flaw
In Python, integers have arbitrary precision (infinite width two's-complement arithmetic). When evaluating `-block_size` in Python:
* `-block_size` is represented conceptually with infinite leading sign bits (`...111110000`).
* When bitwise NOT and two's complement operations interact across 32-bit boundary spaces, or when calculating the broadcast and next available pointer:
```python
# AI computed wildcard mask as:
wildcard_int = ~mask_int  # Returns negative integer in Python (e.g., ~(-256) or ~4294967040)
```
Because Python integers do not truncate to 32 bits, `~mask_int` evaluates to a negative integer (`-4294967041`). When serialized to dotted-decimal notation using standard right shifts (`>> 24`), the sign bit propagates, producing invalid negative octets like `-1.0.0.255` instead of `0.0.0.255`.

### 3. Packet Flow & Network Impact
If negative or non-32-bit bounded integers propagate into Cisco IOS routing statements:
```cisco
! Hallucinated configuration generated by AI logic:
router ospf 1
 network 10.0.4.0 -1.0.0.255 area 0   ! SYNTAX ERROR: Cisco IOS parser rejects invalid wildcard mask
```
* **Packet Flow Analysis:** The router rejects the `network` command upon reload or CLI paste. Interfaces under `10.0.4.0/24` fail to send OSPF `Hello` packets (multicast address `224.0.0.5`). Adjacencies remain in `DOWN` state, causing complete loss of intra-campus inter-VLAN reachability.

### 4. Human Verification & Final Fix
Enforced 32-bit unsigned boundaries on all bitwise inversion and mask calculations by applying explicit 32-bit masking (`& 0xFFFFFFFF`):

```python
# Remediation in netarchitect/vlsm.py
def _calculate_masks(prefix: int) -> tuple[int, int]:
    # Shift 32 bits of 1s, constrained strictly to 32 bits:
    mask_int = (0xFFFFFFFF << (32 - prefix)) & 0xFFFFFFFF
    # Explicit 32-bit bitwise NOT:
    wildcard_int = (~mask_int) & 0xFFFFFFFF
    return mask_int, wildcard_int

# Strict power-of-2 block alignment:
block_size = 1 << (32 - prefix)
current_ptr = (current_ptr + block_size - 1) & ~(block_size - 1)
```

## Audit Entry 2: Security Hallucination on 802.1Q Inter-Switch Trunks

### 1. Context & AI Suggestion
* **Module Affected:** `netarchitect/configgen.py` (Cisco IOS Switch Config Generation)
* **User Prompt:** "Generate Cisco Catalyst IOS configuration for Core and Access trunks interconnecting Building A, B, and C with VLANs 10, 20, and 30."
* **Buggy AI Code Snippet:**
```cisco
interface GigabitEthernet0/1
 description TRUNK-TO-ACCESS-SW01
 switchport mode trunk
 switchport trunk allowed vlan all
 switchport trunk native vlan 1
!
```

### 2. Failure Diagnosis & Technical Flaw
1. **Unconstrained VLAN Pruning:** The AI used `switchport trunk allowed vlan all`. On enterprise multi-building campus switches, allowing all 4,094 VLANs across every trunk breaks traffic isolation, exhausts MAC address tables across disparate switches, and leaks broadcast traffic across unrelated security boundaries.
2. **Default Native VLAN 1:** Retaining default `native vlan 1` exposes the network to double-tagging 802.1Q VLAN hopping attacks (CVE-1999-0775). An untagged frame traversing the trunk can be weaponized with an outer tag matching VLAN 1 and an inner victim tag (e.g., VLAN 99 / Management).

### 3. Packet Flow & Network Impact
* **VLAN Hopping Attack Vector:** An attacker on Access Switch 1 sends a packet with dual 802.1Q headers: Outer tag `VLAN 1`, Inner tag `VLAN 99` (Management).
* **Core Switch Behavior:** The Core switch receives the frame on a trunk where native VLAN is 1. The Core switch automatically strips the outer `VLAN 1` header without inspection and forwards the inner frame onto `VLAN 99`.
* **Result:** Unauthenticated Layer 2 packet injection into the Out-of-Band Management network, bypassing Layer 3 router ACLs and firewalls.

### 4. Human Verification & Final Fix
Refactored `netarchitect/configgen.py` to:
1. Dynamically calculate the precise list of active VLAN IDs and emit an explicit `switchport trunk allowed vlan <id1,id2,...>` list.
2. Re-assign the native VLAN to an isolated, unrouted dead VLAN (`VLAN 999`), and enable trunk pruning.

```python
# Remediation in netarchitect/configgen.py
allowed_vlans_str = ",".join(str(v["id"]) for v in topology["vlans"])
trunk_config = [
    f"interface {trunk_iface}",
    f" description TRUNK-LINK-TO-{remote_peer}",
    " switchport trunk encapsulation dot1q",
    " switchport mode trunk",
    f" switchport trunk allowed vlan {allowed_vlans_str}",  # Never 'all'
    " switchport trunk native vlan 999",                   # Dead isolated native VLAN
    " switchport nonegotiate",                             # Disable DTP to prevent rogue trunk negotiation
    " spanning-tree guard root",
]
```

## Audit Entry 3: Negative Optical Power Budget & Transceiver Misclassification

### 1. Context & AI Suggestion
* **Module Affected:** `netarchitect/media.py` (L1 Media & Distance Physics Engine)
* **User Prompt:** "Recommend transceivers and compute optical budget for links >400m."
* **Buggy AI Code Snippet:**
```python
# AI calculated link loss without transceiver selection thresholds:
if distance_m > 400:
    choice = "10GBASE-LR"  # AI defaulted all single-mode links to 10GBASE-LR
    tx_power = -8.2
    rx_sensitivity = -14.4
    budget = tx_power - rx_sensitivity  # 6.2 dB
    link_loss = (distance_m / 1000) * 0.4
    # AI marked any link with positive loss as OK!
```

### 2. Failure Diagnosis & Technical Flaw
1. **Wrong Transceiver Reach:** `10GBASE-LR` operates at 1310 nm and is IEEE 802.3ae standardized for up to **10 km**. For the Metro MAN profile links (15 km to 35 km), `10GBASE-LR` transceivers will suffer severe optical attenuation and link flapping.
2. **Connector Loss Omission:** The AI completely omitted insertion loss from optical patch panels and LC connectors (standard 0.5 dB per connector pair, 2 connectors minimum per link = 1.0 dB).
3. **Flawed Power Margin Logic:** The AI did not compare link loss against the available optical budget ($P_{\text{margin}} = P_{\text{budget}} - L_{\text{link}}$). For 35 km:
   $$\text{Link Loss} = (35 \times 0.4) + 1.0 = 15.0\text{ dB}$$
   Using LR's 6.2 dB budget results in a **-8.8 dB deficit**!

### 3. Packet Flow & Network Impact
* **Physical Layer Link Degradation:** The receive optical power ($P_{\text{rx}}$) at Site 2 falls far below the receiver sensitivity threshold ($-14.4\text{ dBm}$):
  $$P_{\text{rx}} = -8.2\text{ dBm} - 15.0\text{ dB} = -23.2\text{ dBm} \ll -14.4\text{ dBm}$$
* **Photodiode Desensitization:** The optical receiver photodiode cannot distinguish optical high/low pulses from thermal noise. The link experiences continuous Bit Error Rate (BER) spikes, CRC frame FCS errors, and physical link oscillation (carrier-loss interrupts).
* **Layer 3 Spanning-Tree & OSPF Collapse:** As the physical link flaps, OSPF dead-timers expire, triggering continuous flooding of Link State Updates (LSUs), SPF recalculation storms, and temporary routing blackholes.

### 4. Human Verification & Final Fix
Implemented distance-aware transceiver selection between `10GBASE-LR` (≤10 km) and `10GBASE-ER` (10 km–40 km, 1550 nm laser with +0.5 dBm Tx and -15.8 dBm sensitivity). Programmed explicit power margin math including connector insertion loss:

```python
# Remediation in netarchitect/media.py
if distance_km <= 10.0:
    optics = "10GBASE-LR"
    tx_power_dbm = 0.5
    rx_sensitivity_dbm = -14.4  # Budget = 14.90 dB
else:
    optics = "10GBASE-ER"
    tx_power_dbm = 0.5
    rx_sensitivity_dbm = -15.8  # Budget = 16.30 dB

power_budget = tx_power_dbm - rx_sensitivity_dbm
connector_loss = 2 * 0.5  # 2 patch panel connectors
fiber_loss = distance_km * 0.4  # OS2 0.4 dB/km
total_link_loss = fiber_loss + connector_loss
margin = power_budget - total_link_loss

status = "OK" if margin >= 0 else "INSUFFICIENT — use optical amplifier/EDFA"
```
